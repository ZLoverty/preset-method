# Agent Instruction — P0: SOP Build Baseline & i18n Architecture Audit

## 1. Background

This repository contains an English-language SOP for 3D printing material preset testing.

The SOP is authored in Markdown and built using Pandoc. The repository has recently been migrated from Gitea to GitHub.

The existing documents may contain advanced Markdown and Pandoc features, including:

- Tables with merged rows and columns (`rowspan` / `colspan`)
- Images and figure captions
- LaTeX mathematical expressions
- Pandoc attributes and identifiers
- Cross-references
- Custom templates, filters, and build scripts

The long-term objective is to implement an automated English-to-Simplified-Chinese translation system.

### Long-term requirements

1. English Markdown is the **single source of truth**.
2. Engineers maintain only the English SOP.
3. Chinese translations are generated automatically.
4. Previously approved translations remain stable across builds.
5. Translation Memory (TM) and a terminology glossary control translation consistency.
6. Only new or modified source content requires translation.
7. The translation process must preserve all document structures.
8. Official document builds must not invoke AI translation services.
9. The existing Pandoc build pipeline should be reused wherever possible.
10. The system will eventually integrate with GitHub Actions.

**P0 is an audit and design phase only. Do not implement the translation system in this phase.**

## 6. Task P0.3 — Markdown and AST structure audit

Analyze the actual SOP documents using Pandoc's JSON AST representation.

Where possible, use the same Markdown reader configuration as the production build.

For example:

```bash
pandoc input.md -t json -o output.json
```

This command is illustrative only. Do not assume the default Markdown reader matches the existing build configuration.

Identify all AST node types encountered in the documents.

Pay particular attention to:

| Structure | Audit requirements |
|---|---|
| Header | IDs, levels, attributes |
| Para / Plain | Inline formatting and text boundaries |
| Table | Rowspan, colspan, alignment, captions |
| Image | Source path, caption, alt text, attributes |
| Math | Inline/display math, LaTeX content |
| Code / CodeBlock | Language and attributes |
| Link | URL, title, visible text |
| Div / Span | Custom identifiers and classes |
| Cite | Citation keys and rendering behavior |
| RawInline / RawBlock | Raw LaTeX, HTML or other formats |
| Lists | Nested lists and formatting |
| Footnotes | Note structure and translatable content |

Also identify any structures introduced or modified by custom filters.

### Required analysis

For each relevant node type, determine:

1. Whether it contains translatable natural language.
2. Which fields must remain immutable.
3. Whether inline child ordering may change during translation.
4. Whether the node depends on external filters.
5. Whether translation could invalidate cross-references.
6. Whether the node can be safely reconstructed.
7. Whether the structure requires special P1 handling.

Do not assume that every `Str` node can be translated independently.

Do not assume that every `RawInline` or `RawBlock` can safely be ignored without checking whether it contains visible natural language.

### Deliverable

Create:

`docs/i18n-audit/03-ast-structure-audit.md`

Include:

- AST node inventory
- Representative examples
- Source file locations
- Translation safety classification
- Protected fields
- Unsupported or ambiguous structures
- Proposed extraction boundaries

Use actual examples from the repository.

## 8. Task P0.5 — AST round-trip feasibility

Evaluate whether the existing SOP can safely be processed through Pandoc JSON AST.

Target pipeline:

```text
Markdown
   ↓
Pandoc Reader
   ↓
JSON AST
   ↓
Pandoc Writer
   ↓
Existing Output Format
```

Perform a no-op AST transformation test.

The AST must remain semantically unchanged.

Test whether the output preserves:

- Table geometry
- Merged cells
- Captions
- Image references
- Formula content
- Cross-reference behavior
- Document identifiers
- Custom attributes
- Filter-dependent behavior

Important: distinguish between AST-level preservation and rendered-document equivalence.

A successful JSON round trip alone does not prove that the final PDF or HTML is correct.

If the existing build uses preprocessing or custom filters, test at the appropriate pipeline stage.

Determine whether translation should occur:

- Before custom filters
- Between specific filters
- After selected filters

Provide evidence for the recommended location.

## 9. Task P0.6 — Translation architecture design

Based on the audit findings, propose the architecture for P1 and subsequent phases.

The expected direction is:

```text
English Markdown
       │
       ▼
Pandoc AST
       │
       ▼
Segment Extraction
       │
       ▼
Translation Memory Lookup
       │
       ▼
Translation / Review
       │
       ▼
AST Reconstruction
       │
       ▼
Structure Validation
       │
       ▼
Pandoc Build
       │
       ▼
Chinese SOP
```

However, do not force this architecture if the repository evidence indicates a safer alternative.

Evaluate the following design questions.

### A. Translation granularity

Determine whether the most suitable translation units are:

- Paragraphs
- Headings
- List items
- Table cells
- Captions
- Other structured units

Recommend how to handle mixed inline formatting, such as bold text, links, inline math, citations, and cross-references.

### B. Protected content

Propose how to protect:

- LaTeX expressions
- Parameter identifiers
- Filenames and paths
- URLs
- Cross-reference IDs
- Pandoc attributes
- Code
- Numeric values and units

Identify cases where protected inline content may need to move within a translated sentence without being modified.

### C. Translation memory identity

Evaluate a combination of:

- Canonical source AST hash
- Logical segment identity
- Document context
- Translation status

Explain how translations should be reused when paragraphs move, and invalidated when source content changes.

### D. Translation validation

Propose validation rules for:

- AST structural integrity
- Protected content
- Placeholder consistency
- Tables
- Formulas
- Images
- Cross-references
- Translation completeness

### E. Build reproducibility

Propose how to separate:

- AI-assisted translation updates
- Human translation approval
- Deterministic official builds

Official builds must use approved translations only.

### Deliverable

Create:

`docs/i18n-audit/06-proposed-architecture.md`

The architecture must be grounded in the repository's actual requirements, not merely generic localization practices.
