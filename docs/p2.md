Do not assume that the P1 implementation exactly matches the original specification. Inspect the actual code and use its public interfaces.

### Existing P1 capabilities

P1 provides:

```python
extract_segments(ast, *, source_file="document")
apply_translations(ast, segments, translations)
validate_translation(original_ast, translated_ast, segments)
```

P1 also provides:

- Deterministic segment extraction
- Source-content hashing
- Structured inline placeholders
- Safe reconstruction
- Semantic AST validation
- Atomic translation application
- CLI commands for inspection, extraction, reconstruction and validation

P2 must build upon these capabilities rather than replace them.

### Long-term objective

The English SOP is the only manually maintained source document.

The system must eventually generate a stable Simplified Chinese SOP while ensuring:

1. Approved translations are reused.
2. Unchanged source content is never unnecessarily retranslated.
3. New or modified content is detected automatically.
4. Technical terminology is consistent.
5. Human review controls which translations can enter official builds.
6. Official builds never depend on AI translation services.
7. All translation data is version-controlled in Git.

## 2. P2 objectives

Implement a persistent translation management layer with:

1. Translation Memory (TM)
2. Source-content canonicalization
3. Incremental source matching
4. Translation lifecycle and approval
5. Terminology glossary
6. Translation completeness checks
7. Deterministic translation resolution
8. CLI for updating, reviewing and inspecting translation state
9. Automated tests and documentation

P2 must be fully functional without AI services.

Translations will initially be entered manually or imported from JSON files.

### Core principle

**Translation generation and translation approval are separate operations.**

No newly generated or imported translation may automatically become approved.

Official translation resolution must use approved records only.

```text

├── glossary.yaml
└── memory/

sop_i18n/
├── canonical.py
├── memory.py
├── glossary.py
├── matching.py
├── review.py
```

Adapt the layout to existing repository conventions.

### Requirements

- UTF-8 encoding
- Deterministic serialization
- Stable key ordering
- Human-readable diffs
- Explicit schema version
- Atomic file writes
- No silent data loss
- No hidden state outside Git-tracked files

Temporary files may be used for atomic writes but must not become authoritative data.

The design must support future schema migration.

## 5. Task P2.2 — Canonical source identity

P1 provides `segment_id` and `source_hash`.

P2 must determine whether the existing source hash is suitable for translation memory matching.

### Required analysis

Inspect how P1 computes source hashes.

Check whether hashes change unnecessarily when:

- A paragraph moves to another section.
- A source file is renamed.
- A preceding paragraph is inserted.
- Placeholder numbering changes.
- Equivalent Pandoc AST text representations differ.
- Whitespace is normalized.
- Inline formatting changes.
- A link URL changes while visible text remains unchanged.
- A mathematical expression changes.

### Design requirements

Introduce a canonical translation source identity if necessary.

It should:

- Be independent of AST location.
- Be independent of temporary placeholder numbering.
- Preserve meaningful source-text differences.
- Include protected-content identity where relevant.
- Include formatting structure when it affects reconstruction safety.
- Be deterministic.
- Use an explicit canonicalization version.

For example:

```json
{
  "canonicalization_version": 1,
  "source_key": "sha256:...",
  "source_text": "Record the flow ratio."
}
```

Do not rely on aggressive text normalization that could make materially different source content appear identical.

### Important distinction

A source key identifies reusable source content.

A segment occurrence identifies a location in the current document.

These are not interchangeable.

### Acceptance criteria

- Moving a paragraph does not change its canonical source key.
- Identical source structures generate identical keys.
- Materially different protected content generates different keys.
- Temporary placeholder numbering does not cause unnecessary cache misses.
- Canonicalization is deterministic across runs.

## 6. Task P2.3 — Translation Memory schema

Implement a persistent TM.

Recommended conceptual record:

```json
{
  "record_id": "tm_000001",
  "language": "zh-CN",
  "source_key": "sha256:...",
  "source": "Record the flow ratio.",
  "target": "记录流量比。",
  "status": "approved",
  "context": {
    "document": "printer-calibration",
    "section": "Flow Ratio"
  },
  "source_schema_version": 1,
  "created_at": "2026-10-15T00:00:00Z",
  "updated_at": "2026-10-15T00:00:00Z",
  "reviewed_at": "2026-10-15T00:00:00Z"
}
```

This is a conceptual schema. Refine it as needed.

### Required fields

- Record ID
- Target language
- Canonical source key
- Original source representation
- Translated token representation
- Review status
- Context metadata
- Schema version
- Creation and modification metadata

### Review states

Support at least:

- `draft`
- `approved`
- `rejected`

Define legal transitions explicitly.

Recommended transitions:

```text
draft → approved
draft → rejected
rejected → draft
approved → draft (explicit revision)
```

Editing an approved translation must not silently preserve its approved status.

A revised translation must undergo approval again.

### History and auditability

Since Git is the version history, do not implement an unnecessarily complex internal revision system.

However, each record must have a stable ID and explicit review metadata.

Preserve previous records when necessary to avoid destructive replacement.

### Duplicate source content

Allow multiple translations for the same source key when contexts differ.

Do not assume that one English sentence always has exactly one correct Chinese translation.

## 7. Task P2.4 — Incremental source synchronization

Implement synchronization between current P1 segments and the translation memory.

The synchronization process must classify source occurrences.

Required categories:

| Category | Meaning |
|---|---|
| MATCHED | Approved translation resolved |
| DRAFT | Matching translation exists but is not approved |
| MISSING | No translation record exists |
| CHANGED | Related previous source exists but source content changed |
| AMBIGUOUS | Multiple possible translations without a unique selection |
| OBSOLETE | TM record is not referenced by the current source |

### Matching priority

Use a deterministic strategy.

Recommended order:

1. Exact source key and exact context
2. Exact source key and explicitly compatible context
3. Unique approved exact source key with no conflicting context
4. Otherwise unresolved

Never select an arbitrary record based on file order.

### Changed source

When English content changes:

- Do not reuse an old translation as approved automatically.
- Mark the new occurrence as requiring review.
- Preserve the previous approved record.
- Optionally identify the previous translation as a reference for the reviewer.

Fuzzy matching may be used for suggestions, but must not automatically approve a translation.

### Obsolete records

Do not automatically delete obsolete translations.

Report them separately.

A translation may become useful again if source text is restored.

### Idempotency

Running synchronization repeatedly without source changes must not create duplicate records or modify files unnecessarily.

### Acceptance criteria

- Unchanged source content reuses approved translations.
- Moved content can reuse translations.
- Changed source content requires review.
- Obsolete records remain available.
- Ambiguous matches fail closed.
- Repeated synchronization is idempotent.

## 8. Task P2.5 — Translation review operations

Implement a local review workflow.

### Required operations

- Create draft translation
- Update draft translation
- Approve draft
- Reject draft
- Reopen rejected draft
- Revise approved translation through a new review cycle
- Inspect record history metadata

### Approval requirements

Before approval:

1. Validate placeholder integrity using P1.
2. Validate protected-content preservation.
3. Validate that the record matches its canonical source.
4. Run applicable glossary checks.
5. Reject malformed translations.

Approval must not be a simple status change without validation.

### Review metadata

Support:

- Reviewer identity
- Review timestamp
- Optional review comment

Do not require a network identity provider.

A local reviewer name may be supplied explicitly through the CLI.

### Safety

A rejected translation must never be used by the official resolver.

A draft translation must never be used by the official resolver.

An approved translation that no longer matches its source key must never be used.

## 9. Task P2.6 — Glossary

Implement a terminology glossary for English-to-Simplified-Chinese translation.

Suggested schema:

```yaml
schema_version: 1
language: zh-CN

terms:
  - id: flow-ratio
    source: Flow Ratio
    target: 流量比
    match_mode: phrase
    severity: warning

  - id: pressure-advance
    source: Pressure Advance
    target: 压力提前量
    match_mode: phrase
    severity: warning

  - id: preset
    source: Preset
    target: 预设
    match_mode: phrase
    severity: warning
```

The entries are initial examples, not an authoritative terminology list.

Inspect actual SOP terminology and propose a glossary based on terms used in the repository.

Do not silently rewrite existing English or invent translations for ambiguous technical terms.

### Glossary capabilities

- Load and validate glossary configuration.
- Match source terms.
- Check corresponding target terminology.
- Report missing preferred translations.
- Support allowed alternatives where appropriate.
- Support case sensitivity and whole-word/phrase matching.
- Exclude protected code, math and identifiers from natural-language matching.
- Produce structured diagnostics.

### Important limitations

Chinese terminology checks cannot rely solely on naive substring matching.

Avoid claiming semantic correctness from lexical matching alone.

Glossary checking is a review aid, not a complete translation-quality evaluator.

### Severity

Support:

- `error`
- `warning`
- `info`

Only configured errors should block approval.

Warnings should remain visible to reviewers.

## 10. Task P2.7 — Deterministic translation resolution

Implement a resolver that takes:

- Current P1 segments
- Translation memory
- Target language
- Context

And produces:

```python
translations: dict[str, str]
```

The mapping must be compatible with P1:

```python
apply_translations(
    ast,
    segments,
    translations,
)
```

### Strict mode

Implement a strict resolution mode for future official builds.

Strict mode must:

- Use approved translations only.
- Require a unique valid match.
- Reject missing translations.
- Reject ambiguous matches.
- Reject invalid placeholders.
- Reject stale source keys.
- Produce a complete diagnostic report.

No partial success should be reported as a valid official translation.

### Preview mode

Optionally support a preview mode that reports unresolved segments without producing a production-approved output.

If preview reconstruction uses source-text fallbacks, mark the result explicitly as incomplete and unsuitable for publication.

Do not silently substitute English text in official Chinese output.

### Determinism

Given the same:

- Source AST
- TM data
- Glossary
- Configuration
- Canonicalization version

The resolver must produce identical results.

No network calls, timestamps or randomness may affect resolution.

These are suggested interfaces, not mandatory exact syntax.

### CLI requirements

- Support explicit source and TM paths.
- Default to repository configuration where safe.
- Provide `--help`.
- Return nonzero exit codes for errors.
- Avoid overwriting files without explicit permission.
- Print useful diagnostic messages.
- Support JSON output for machine-readable reports.
- Work without AI API keys.
- Work on Windows and Linux.
- Avoid shell-specific assumptions.

### Recommended workflow

```text
Inspect source
      ↓
Sync TM
      ↓
Export missing drafts
      ↓
Manually edit translations
      ↓
Import drafts
      ↓
Review and approve
      ↓
Strict resolve
      ↓
P1 reconstruction
```

## 12. Task P2.9 — Automated tests

Add comprehensive unit and integration tests.

### Canonicalization tests

- Identical source produces identical key.
- Moving a segment does not change key.
- Changing source text changes key.
- Changing protected math changes key.
- Changing link destination changes key.
- Placeholder renumbering does not change key.
- Equivalent canonical input produces stable serialization.
- Unsupported canonicalization version is rejected.

### Translation memory tests

- Create draft.
- Approve draft.
- Reject draft.
- Reopen rejected draft.
- Revise approved translation.
- Preserve approved record during source changes.
- Support duplicate source with different contexts.
- Detect ambiguous matches.
- Preserve obsolete records.
- Atomic file writes.
- Idempotent synchronization.
- Reject malformed schema.

### Glossary tests

- Exact phrase matching.
- Case sensitivity.
- Whole-word matching.
- Allowed alternatives.
- Protected-content exclusion.
- Warning and error severities.
- Invalid glossary configuration.

### Resolver tests

- Approved exact match.
- Draft not accepted in strict mode.
- Rejected not accepted in strict mode.
- Missing translation.
- Changed source.
- Ambiguous translation.
- Stale source key.
- Deterministic output.
- Complete mapping compatible with P1.

### Integration tests

Use actual SOP content and the real `sop/pdf-order.txt` document ordering.

Test:

1. Extract current segments.
2. Synchronize translation memory.
3. Generate missing draft entries.
4. Import manually supplied test translations.
5. Approve test translations.
6. Resolve approved translations.
7. Reconstruct the Pandoc AST using P1.
8. Validate structural integrity.

Use temporary TM files for tests.

### Regression tests
