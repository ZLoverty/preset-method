# P3.1 OpenAI Online Provider

## Scope and safety

P3.1 adds an optional online provider behind the existing P3 boundary. The
provider is implemented with Python's standard-library HTTPS client, so the
offline P1–P4 workflows do not require the OpenAI SDK or credentials. It reads
`OPENAI_API_KEY` (or `API_KEY`) from the process environment, then from the
local `.env` file, and never writes TM, changes review states, edits Markdown,
or approves translations. The `.env` parser only reads simple `KEY=value`
entries; it never executes shell content. Process environment variables take
precedence.

The endpoint is the OpenAI Responses API. Requests use the existing
`i18n/prompts/zh-CN-v1.txt` policy and Responses structured output with a strict
JSON Schema containing `schema_version` and `translations[{job_id,target}]`.
Responses are still parsed by the existing P3 `parse_response` implementation;
API-side schema enforcement is not treated as local validation.

## CLI

First generate jobs using P3. Then run the provider explicitly:

```text
python -m sop_i18n translate run \
  --jobs tmp/translation-jobs.json \
  --run-dir tmp/i18n-runs/run-001 \
  --model MODEL_ID \
  --glossary i18n/glossary.json
```

Optional controls include `--max-jobs`, `--max-request-bytes`, `--timeout`,
`--retries`, `--initial-backoff`, `--max-backoff`, `--endpoint`,
`--prompt-version`, `--pricing`, `--max-cost`, and `--no-resume`.

The API key is never accepted as a CLI argument and is never printed. By
default the command reads `.env`; use `--env-file PATH` to select another
dotenv file. The
default endpoint is `https://api.openai.com/v1/responses`; a custom endpoint is
available for compatible gateways.

## Batching, retries and resumability

`partition_jobs` preserves stable job order, enforces both job-count and UTF-8
request-size limits, and rejects an individual oversized job. Retries are
bounded and apply only to HTTP 429/5xx and network failures. Exponential
backoff includes jitter and honors `Retry-After` when available. Invalid
credentials, malformed local artifacts and schema/identity failures are not
retried.

Each run stores an atomic manifest, one atomic batch candidate artifact,
combined candidates and a report. The manifest fingerprints the job artifact,
model, prompt, policy and batch settings. Resume skips only a completed batch
whose job IDs exactly match the current partition and whose manifest matches.
Changing source jobs, model, prompt or limits requires a new run directory.

## QA and provenance

After each response, candidates are passed through the existing P3
`validate_candidate` function. Structural, placeholder, numeric/unit and
glossary errors are recorded as failed candidates and cannot be imported by
the existing draft importer. No automatic repair request is made.

Candidate provenance records provider, model and prompt version. Usage reports
request count, successful/failed requests, retries, input/output/total tokens
and elapsed time. Optional pricing JSON supports input/output USD per million
tokens and an optional maximum estimated cost. Without pricing, no cost is
invented.

## Limitations

- Sequential execution is intentional; concurrency is not used.
- The provider does not discover model pricing.
- The API key, account permissions and model availability are external
  requirements.
- No real API call is made by automated tests.
- Online candidates still require P3 draft import and P2 human approval before
  P4 can consume them.
