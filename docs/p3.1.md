# Agent Instruction — P3.1: Online AI Translation Provider

## 1. Background

Repository: `preset-method`

P1–P4 have been implemented.

The existing translation architecture is:

```text
English Markdown
    ↓
P1 Pandoc AST extraction
    ↓
P2 Translation Memory matching
    ↓

    ↓
P3 Offline translation exchange
    ↓
P3 Candidate QA
    ↓

    ↓
```

P3.1 adds online AI translation to the existing P3 provider boundary.

## 2. Objective

Implement an online translation provider that can:

1. Read existing P3 translation jobs.
2. Call a configurable AI API.
3. Translate jobs in bounded batches.
4. Parse structured responses.
5. Validate response identities.
6. Save candidate artifacts incrementally.
7. Retry transient failures.
8. Resume interrupted runs.
9. Estimate or report API usage.
10. Integrate with existing P3 QA and draft import.

The online provider must never directly approve translations.

### Intended workflow

```text
P3 translate plan
       ↓
P3.1 translate run
       ↓
AI API
       ↓
Raw structured response
       ↓
P3 Candidate parsing
       ↓
P3 QA
       ↓
Validated candidates
       ↓
P3 import-drafts
       ↓
P2 Human approval
```

## 4. Task P3.1.1 — Provider selection

Implement one production-ready provider using the official OpenAI API.

Use the current documented API contract rather than guessing endpoint fields.

Prefer the Responses API with structured JSON output if supported by the selected model.

The provider must be isolated behind the existing P3 `TranslationProvider` protocol.

Suggested layout:

```text
sop_i18n/
  providers/
    __init__.py
    openai.py
    errors.py
```

Do not make the entire package depend on the OpenAI SDK merely to run P1–P4.

An optional dependency is acceptable.

### Configuration

Support:

- Provider: `openai`
- Model: user-configurable
- API key from `OPENAI_API_KEY`
- Optional project/organization configuration if supported
- Request timeout
- Maximum jobs per batch
- Maximum request size
- Retry count
- Prompt version

Do not hardcode an API key or require one for offline workflows.

## 5. Task P3.1.2 — API request and response contract

Use the existing versioned translation prompt:

`i18n/prompts/zh-CN-v1.txt`

Do not silently modify the prompt.

If changes are necessary, introduce `zh-CN-v2.txt` and update the configured prompt version.

### Request content

Each request should include:

- Translation policy
- Target language
- Job IDs
- Source text
- Placeholder-bearing text
- Relevant glossary entries
- Bounded heading context
- Neighboring context
- Optional previous translation

Send only data required for translation.

Do not send entire repository files.

### Response format

Require a structured response equivalent to:

```json
{
  "schema_version": 1,
  "translations": [
    {
      "job_id": "job_...",
      "target": "中文译文"
    }
  ]
}
```

Use API-supported structured output where available.

Validate responses locally regardless of API schema enforcement.

### Failure conditions

Reject:

- Missing job IDs
- Duplicate job IDs
- Unknown job IDs
- Missing target text
- Unexpected response structure
- Invalid JSON
- Truncated output
- Refusal or incomplete response
- Wrong target language when detectable

Do not silently accept partial batch responses.

## 6. Task P3.1.3 — Batching

Implement deterministic batching.

### Requirements

- Stable job ordering
- Configurable maximum jobs per batch
- Configurable request-size limit
- Preserve job IDs
- Never split one job across batches
- Avoid excessively large prompts
- Record batch membership

### Suggested defaults

- 10–20 jobs per batch
- Conservative request-size limits
- Sequential execution initially

Do not introduce concurrency until sequential execution is reliable.

### Acceptance criteria

- Same job set produces the same batch partition under the same configuration.
- No job is omitted.
- No job is duplicated.
- Context size is bounded.
- Oversized individual jobs fail with a useful diagnostic.

---

## 7. Task P3.1.4 — Retry and rate limiting

Implement bounded retries for transient failures.

Retryable examples:

- HTTP 429
- HTTP 500/502/503/504
- Network timeouts
- Temporary connection failures

Non-retryable examples:

- Invalid API key
- Invalid request schema
- Unsupported model
- Permission denied
- Malformed local job artifact

### Backoff

Use exponential backoff with jitter.

Respect server-provided retry hints when available.

Configure:

- Maximum retries
- Initial delay
- Maximum delay

Never retry indefinitely.

### Safety

Do not log credentials.

Do not include raw authorization headers in error reports.

Preserve useful error messages without exposing secrets.

## 8. Task P3.1.5 — Resumable execution

Translation runs must survive interruption.

Suggested directory:

```text
tmp/i18n-runs/<run-id>/
  manifest.json
  batches/
    batch-0001.json
    batch-0002.json
  candidates.json
  report.json
```

These are generated artifacts, not authoritative TM records.

Add suitable ignore rules without hiding source files or approved TM data.

### Manifest

Record:

- Job artifact hash
- Model
- Provider
- Prompt hash
- Glossary hash
- Translation policy version
- Batch configuration
- Run configuration fingerprint

### Resume behavior

On resume:

1. Load the manifest.
2. Verify configuration compatibility.
3. Validate saved completed batches.
4. Skip completed valid batches.
5. Retry missing or failed batches.
6. Merge validated candidates deterministically.

Do not reuse cached results when source keys, prompt, model or relevant glossary inputs differ.

### Atomicity

Write each completed batch atomically.

A partially written batch must not be treated as complete.

### Idempotency

Rerunning a completed run should not make new API calls unless explicitly requested.

## 9. Task P3.1.6 — Local QA integration

Do not implement a separate online-provider QA engine.

Reuse existing P3 candidate validation.

After each successful API response:

1. Parse the structured response.
2. Match responses to jobs.
3. Construct P3 candidates.
4. Attach provenance.
5. Run existing P3 QA.
6. Persist results.

### Validation policy

- Structural errors block candidate acceptance.
- Missing placeholders block acceptance.
- Numerical/unit mismatches block acceptance.
- Glossary errors block acceptance.
- Warnings remain visible.
- Failed candidates remain available for diagnostics but cannot be imported as drafts.

### Important

Do not automatically ask the AI to repair failed translations in this phase.

Report QA failures and allow explicit reruns.

This prevents unexpected API spending and uncontrolled output changes.

## 10. Task P3.1.7 — Usage and cost reporting

Capture usage data returned by the provider.

At minimum:

- Request count
- Successful requests
- Failed requests
- Retried requests
- Input tokens
- Output tokens
- Total tokens
- Elapsed time

### Cost estimation

Support optional user-configured pricing:

```json
{
  "input_per_million_tokens_usd": 0.0,
  "output_per_million_tokens_usd": 0.0
}
```

These values are placeholders, not real prices.

If pricing is not configured, report token usage without inventing costs.
