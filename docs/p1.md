# Agent Instruction — P1: Pandoc AST Translation Core

## 1. Background

Repository: `preset-method`

P0 audit has been completed. Its findings and architecture recommendations are documented in:

- `docs/i18n-audit/README.md`
- `docs/i18n-audit/03-ast-structure-audit.md`
- `docs/i18n-audit/05-ast-roundtrip.md`
- `docs/i18n-audit/06-proposed-architecture.md`
- `docs/i18n-audit/07-p1-specification.md`

Read these documents before implementation.

The repository contains an English SOP written in Markdown and built into PDF using Pandoc and XeLaTeX.

The long-term goal is to maintain English Markdown as the single source of truth while automatically producing a stable, reviewed Chinese translation.

P1 establishes the structural foundation for translation.

**Do not implement AI translation, translation memory, glossary management, or GitHub Actions integration in P1.**

## 2. P1 Objectives

Implement a reusable Python module that can:

1. Parse or accept Pandoc JSON AST.
2. Extract translatable natural-language segments.
3. Represent protected inline content using structured placeholders.
4. Accept replacement translations for extracted segments.
5. Reconstruct a translated Pandoc AST.
6. Validate structural and protected-content integrity.
7. Produce clear diagnostics for unsupported or unsafe structures.
8. Provide a CLI for inspection and testing.
9. Pass automated tests using actual SOP examples.

The system must preserve the original AST and must not modify source Markdown.

### Core principle

Translation is permitted to modify natural-language content only.

It must not modify:

- Document structure
- Mathematical expressions
- Code
- Image paths
- Link destinations
- Cross-reference identifiers
- Pandoc attributes
- Table geometry
- Other protected technical content

## 5. Task P1.2 — Segment data model

Design a structured `Segment` model.

Recommended fields:

```python
@dataclass(frozen=True)
class Segment:
    segment_id: str
    source_text: str
    source_hash: str
    ast_path: tuple
    node_type: str
    context: dict
    placeholders: tuple
```

The final model may differ, but it must support:

- Stable identification within a document
- Source-content hashing
- AST location tracking
- Translation context
- Protected inline elements
- Safe reconstruction

### Identity requirements

Distinguish between:

1. Segment occurrence identity
2. Canonical source-content hash

Two identical English paragraphs may occur at different locations.

They may share a source hash but must remain distinguishable as AST occurrences.

Moving a paragraph should not necessarily invalidate a future translation memory match.

Do not rely solely on a positional AST path as the permanent translation identity.

For P1, deterministic occurrence IDs are sufficient. Design the model so that P2 can introduce persistent logical IDs without breaking compatibility.

## 6. Task P1.3 — AST extraction

Implement traversal of the Pandoc JSON AST.

Use the repository's actual Pandoc reader configuration when parsing Markdown.

Do not assume default Markdown extensions.

### Initial translatable structures

Support, where present:

- `Header`
- `Para`
- `Plain`
- `BulletList`
- `OrderedList`
- `BlockQuote`
- `Table` cell contents
- `Figure` captions
- `Image` alt text or captions
- `Note` contents
- Text inside supported `Div` and `Span` structures

Avoid duplicate extraction when a caption or nested structure is represented by multiple AST layers.

### Extraction granularity

Use semantic text units rather than individual `Str` nodes.

For example:

```markdown
Use **Flow Ratio** to calibrate the printer.
```

Should produce one logical segment, not multiple independent segments.

For lists, extract text at the appropriate paragraph or Plain level, preserving list structure.

For tables, extract natural language from individual cell blocks while preserving the table structure.

For captions, distinguish visible caption text from structural identifiers.

### Unsupported structures

Unknown nodes must not be silently treated as successfully translated.

Implement explicit handling classifications:

- TRANSLATABLE
- PROTECTED
- STRUCTURAL
- UNSUPPORTED

For unsupported nodes containing potentially visible natural language, generate a diagnostic.

Fail closed when translation safety cannot be established.

## 7. Task P1.4 — Protected inline content

Implement structured placeholders for inline content that must not be translated.

Protected content includes:

- Inline mathematics
- Display mathematics
- Inline code
- Cross-reference tokens
- Link destinations and titles
- Image paths
- Pandoc identifiers and attributes
- Technical parameter identifiers
- Numeric values and units, where reliably identifiable

### Important design distinction

Not all inline elements should be protected as opaque objects.

For example, the visible text of a link may be translatable, while its URL must remain unchanged.

Similarly, bold and italic text should remain translatable while preserving formatting.

The implementation must distinguish:

1. Opaque protected content
2. Translatable content with formatting
3. Structural metadata

### Example

Source:

```markdown
Set **Flow Ratio** to `0.95` and refer to
[the calibration guide](calibration.md).
```

The extraction representation may resemble:

```text
Set <strong id="1">Flow Ratio</strong>
to <protected id="2"/> and refer to
<link id="3">the calibration guide</link>.
```

This is conceptual notation, not a required serialization format.

The representation must allow translated text to change word order.

### Placeholder integrity

Validate that:

- Every required placeholder remains present.
- No unknown placeholder is introduced.
- No protected placeholder is duplicated or omitted.
- Placeholder identity is preserved.
- Nesting is valid.
- Formatting scopes are well formed.
- Protected payloads remain unchanged.

Do not require the original placeholder order if reordering is semantically valid.

Use an explicit parser or structured representation for placeholders. Do not rely solely on naive string replacement.

## 8. Task P1.5 — Reconstruction

Implement translation application without modifying the original AST.

### Required behavior

- Deep-copy the source AST.
- Locate the target segment.
- Validate the translated segment representation.
- Reconstruct the corresponding inline subtree.
- Preserve structural metadata.
- Preserve protected objects.
- Reject invalid replacements.

### Example

Original:

```markdown
Use **Flow Ratio** to calibrate the printer.
```

Translated:

```markdown
使用 **流量比** 校准打印机。
```

The resulting AST may contain different `Str` and `Space` node counts.

This is allowed.

The following must remain intact:

- `Strong` formatting semantics
- Surrounding document structure
- Node attributes
- Other protected inline content

### Atomicity

Translation application must be atomic from the caller's perspective.

If any segment fails validation:

- Return a structured error.
- Do not return a partially translated AST as successful output.
- Do not modify the input AST.

For batch operations, either reject the complete batch or explicitly expose a separate partial-result API. The default production path must reject incomplete application.

## 9. Task P1.6 — Structural validation

Implement a validator that compares the original and translated AST.

Do not require byte-for-byte equality.

### Immutable elements

Verify preservation of:

- Document metadata not explicitly marked translatable
- Header levels and IDs
- Table row/column geometry
- Rowspan and colspan
- Table alignment
- Image targets and attributes
- Link destinations
- Math payloads
- Code payloads
- Div/Span identifiers and attributes
- Citation identifiers
- Raw nodes
- List structure
- Cross-reference targets

### Allowed changes

Permit:

- Natural-language text changes
- Different `Str` node counts
- Different `Space` node counts
- Reordering of valid inline placeholders
- Text changes inside supported formatting scopes
- Other explicitly permitted translatable content changes

### Validation strategy

Do not implement a single blanket recursive equality check.

Use a semantic comparison that separates:

1. Immutable structural information
2. Protected payloads
3. Allowed translatable text regions

The validator must detect accidental changes even if they occur outside the explicitly translated segments.

### Diagnostics

Each validation error should include:

- Error code
- Severity
- Segment ID, if applicable
- AST path
- Description
- Expected invariant
- Observed violation

## 10. Task P1.7 — CLI

Implement a minimal CLI.

Suggested commands:

```bash
python -m sop_i18n inspect
python -m sop_i18n extract
python -m sop_i18n validate
```

### Inspect

Report:

- Source files analyzed
- AST node types
- Translatable segment counts
- Protected element counts
- Unsupported structures
- Extraction coverage

### Extract

Export extracted segments to a machine-readable JSON file.

Include enough context for later translation review.

Do not export mutable AST references or non-serializable Python objects.

### Validate

Validate an original AST and a candidate translated AST.

Return a nonzero exit code for structural violations.

### CLI requirements

- Use clear help messages.
- Support explicit input/output paths.
- Avoid hard-coded absolute paths.
- Do not overwrite existing files without explicit permission.
- Do not write to the SOP source directory.
- Use the repository's actual source ordering and reader extensions.
- Report unsupported constructs rather than silently skipping them.
